# 端到端用户体验设计

状态：流程与文案提案，未实现。本文是产品体验的主线，技术方案应服务于这里定义的交接和恢复行为。

## 1. 核心体验承诺

**用户交代目标，系统承担操作成本；需要人介入时交代清楚，回来时接得上。**

用户在任何时刻都应该能回答：

1. 现在是谁在控制手机？
2. 正在做什么，在等什么？
3. 是否需要我处理？
4. 我如何立即拿回控制？
5. 停下来以后，已经完成的部分会怎样？

减少不必要的确认、输入和切换，优先于增加任务模板数量。

## 2. 入口与目标表达

聊天输入区提供「控制此手机」，设置页提供「手机连接」。用户可直接描述目标，也可从自己选定的当前页面开始。

- 先接受目标，再按需补齐设备准备；不把尚未连接当作丢弃目标的理由。
- 当前页面作为上下文时，由用户主动选择或在已有观察授权下读取，不在输入意图前静默采集屏幕。
- 能从目标和已有上下文推断的信息，不再次询问。
- 同名 App、目标位置或修改内容的歧义会影响执行时，合并成一个简短问题。
- 不要求用户逐步提供点击坐标、包名或界面路径。
- 通用示例仅帮助表达“查找、整理、编辑、导航”等能力，不预设支持特定服务。

开始前给出一行可编辑的目标摘要，而非让用户审查几十步计划。已有有效授权且目标明确时直接执行；需要补充授权或条件时再展示开始入口。

## 3. 首次使用：把设置做成可接续的向导

### 3.1 分步而非一次性说明书

1. **检测**：说明设备/运行模式是否支持，以及还差什么。
2. **解释**：一次性说明会切换 App，页面内容可能进入当前模型上下文。
3. **引导**：一次只给一个系统设置动作；支持的设置页提供快捷跳转，其他情况用短路径提示。
4. **配对**：专门的结构化表单接收端口与临时配对码，字段命名与系统页面一致。
5. **验证**：确认传输与必要能力可用，显示可以开始的状态。
6. **接回目标**：恢复最初的任务摘要，不要求重新输入。

### 3.2 跨设置页的体验

- 离开宿主进入设置时保留当前步骤和非敏感草稿。
- 用户返回后自动检查完成条件，不机械要求重复走完整向导。
- 可评估通知上的返回引导与可选的小窗辅助，但不依赖新增悬浮权限才能完成配对。
- 自动发现优先；手动连接信息放在回退路径，清楚区分配对端口与连接端口。
- 配对码过期只重做配对步骤；已完成的设置不重复要求。
- 配对码不进聊天、不进日志、不永久保存，失败或过期后清除。

首次授权不可避免的成本需要解释，但不能让技术术语成为日常使用入口。

## 4. 日常使用：准备过程尽量隐去

已配置用户表达目标后，系统先在后台做就绪检查。正常时显示简短“准备执行”并继续；存在阻碍时只显示当前缺少的一步。

| 情况 | 用户体验 |
| --- | --- |
| 连接、设备与授权都正常 | 直接进入执行，不再展示向导 |
| 已配对但连接地址变化 | 有界自动发现和重连；失败后给具体恢复操作 |
| 无线调试被关闭 | 保留目标，提示开启位置；返回后重新检测 |
| 另一会话正在操作 | 显示当前拥有者，允许用户返回该任务或明确交接 |
| 设备未解锁 | 等待用户解锁，说明不会在锁屏上继续操作 |

恢复传输不自动恢复已被接管或撤销的控制权。后台检查不能无限显示转圈；超过阶段时间预算时显示正在等待的原因及可选操作。

## 5. 交接控制：避免突然切走

任务开始时，持久显示简短摘要：目标、当前 App、控制者和暂停/接管入口。首次开始需让用户知道手机将切换到目标 App，后续不逐步弹确认框。

执行中的控制面分工：

| 界面 | 责任 |
| --- | --- |
| 聊天任务卡 | 完整目标、阶段、需要用户处理的事项、结果 |
| 系统通知 | 跨 App 可达的暂停/停止/返回任务入口 |
| 可选悬浮控制条 | 在设备和权限允许时提供更快的接管入口 |

通知权限不可用时必须有经验证的替代接管入口；否则先引导补齐条件，不启动没有可靠控制入口的任务。

悬浮控制条不能遮住目标控件，其拖动和按钮不能成为 Agent 的目标。最终形态根据真机遮挡、误触和可达性测试决定，不让新增权限成为默认负担。

## 6. 执行等待：展示意义，不展示流水账

任务卡建议只呈现：

```text
目标：用户确认的目标摘要
阶段：正在查找需要的内容
当前 App：用户所选应用
最近进展：已找到目标区域，正在读取
需要你处理：暂无

[暂停]  [我来操作]
```

- 以“准备、查找、处理、核对”为阶段，避免每次点击都刷出一张卡。
- 区分模型思考、App 加载、设备重连和等待用户，不把所有等待都写成“处理中”。
- 显示实际最新更新时间；无新证据时不刷新假进度，不显示虚构百分比。
- 慢任务给出等待原因与下一步；没有测量依据时不承诺剩余秒数。
- 细节和动作记录可展开，默认只展示与用户目标有关的信息。
- 状态从同一任务事件源派生，聊天、通知和控制条不能各自猜测“已完成”。

## 7. 人工介入：让交接尽量短

### 暂停、接管、停止

- **暂停**：停止接纳新的修改动作，保留目标和已验证进度。
- **我来操作**：交还修改权限，用户可以在 App 中自行处理；继续按钮保持可达。
- **停止任务**：结束目标，不再自动继续；显示已完成和无法确认的部分。

点击后先反馈“正在暂停”或“正在交还控制”，收到执行层确认后再显示“已暂停”或“你正在控制”。如果动作已经派发，明确它可能仍在生效；不能把停止说成回滚。

不要承诺能自动辨认所有跨 App 触摸来源。首版提供明确接管入口；检测到意外窗口变化时停止使用旧引用并重新核对。

### 需要用户处理时

只请求当前必要的一步，说明原因、入口和完成后的继续方式。例如登录由用户完成，Agent 在此期间停止观察和修改，避免采集输入内容；用户选择继续后再重新观察。

需要决策时，保留现场并提供简短选择。不要反复把用户拉回聊天，再要求手动回到目标页面寻找刚才的位置。

### 用户改变目标

用户在对话中修正目标时，先停止与新目标冲突的动作，展示会影响后续执行的变化。已明确完成的事实保留，不能把全部任务清零，也不能把旧提交误当成可以重做。

## 8. 从中断处继续

```text
就绪 → 执行中 → 核对结果 → 已结束
          │
          ├→ 暂停中 → 已暂停 → 重新观察 → 执行中
          ├→ 交接中 → 用户操作 → 用户继续 → 重新观察
          ├→ 断连/锁屏 → 恢复条件 → 用户继续 → 重新观察
          └→ 效果不明 → 仅观察 → 用户核对后继续或结束
```

恢复依次完成：

1. 重新验证连接和会话所有权。
2. 读取当前界面，失效旧 refs、截图坐标与窗口假设。
3. 对照任务目标、已确认的进度与未决动作。
4. 未改变关键条件时，从可验证的下一步继续。
5. 目标、目的地或提交条件变了才简短询问。

连接恢复不等于动作失败，也不等于动作成功。已派发但无法核对的动作保持未决，不自动重做。进程重启后若只保留了目标摘要，应直接说明无法恢复哪些进度。

恢复卡片以“保留了什么、需要你做什么”组织，不要求用户理解租约、epoch 或请求 ID。

## 9. 结果交付：先结论，再依据

任务结束先停止后续修改并交还控制，再呈现结果。设备断连时说明控制已结束但最终页面无法读取，不伪装为完成。

结果卡至少区分：

| 状态 | 内容 |
| --- | --- |
| 已完成 | 完成了什么、依据、结果所在位置 |
| 部分完成 | 已完成部分、未完成部分、下一步 |
| 等待外部处理 | 已进行到哪一步，尚不能确认的最终结果 |
| 无法确认 | 可能已经发生的动作、可核对入口 |
| 已停止/未能完成 | 停止原因、已发生的部分、是否需要用户收尾 |

不把成功派发点击当成用户目标已完成。证据默认是必要的文字摘录和时间，截图按需展开。

默认保留目标 App 的最终页面，不突然抢回聊天；通知可打开结果。若支持“完成后返回聊天”的偏好，需要用户选择并验证系统允许。用户没有发起下一目标时，不自动启动下一项工作。

## 10. 体验验证

用独立构造的任务原型和合成数据测试，不复用用户聊天中的经历。

- **首次使用**：能否不依赖口头指导完成设置，返回后是否还记得原目标？
- **再次使用**：是否还会要求输入技术参数或重复确认？
- **等待**：用户是否分得清正常执行、加载、重连和等待自己？
- **接管**：能否找到入口，是否理解接管已经生效？
- **恢复**：是否需要重述目标，是否重做已完成的部分？
- **收尾**：能否正确说出完成范围、仍未确认的部分和自己的下一步？

记录每条链路的完成率、步骤数、切换次数、耗时、误解和放弃位置。暂停/接管的可见反馈以 300ms 内为初始交互目标，与真正停止接纳动作的时间分开测量；这是设计目标，不是当前性能承诺。

## 11. 视觉与可访问性

优先可读的阶段文字、清晰的主操作和稳定位置的接管入口。颜色不能是状态的唯一信号；为大字体、屏幕阅读器、单手操作和通知受限场景设计回退路径。
